## 三、候选流式渲染（零等待）专章

### 3.1 大厂常规做法

1. **本地增量出候选**：每敲一个音节就查一次表，先出这一小段的结果，不排序全量。
2. **首屏优先**：先算够一屏（5～9 条）就上屏，后续候选在后台继续补，补到再追加。
3. **渲染不等全量**：候选窗**先出现**（定位＋首屏），再逐帧追加/局部重绘；重算不阻塞窗口。
4. **云端或 AI 结果后到后插**：不阻塞本地首屏，到货了插在合适位置或另起一段。

### 3.2 我们已有什么

来源：`PROGRESS.md` 六·二十七（懒菜单 v3 + 甲-1a `Translation` 抽象层）。

| 环节 | 现在流式到哪一步 | 证据 |
|---|---|---|
| 菜单物化 | 按需补到第 k 条，不碰后面的 | `menu.rs:94-114` |
| 分页物化 | **每键只物化 1 页**（`page_size` 条），再多取 1 条判末页 | `menu.rs:140-153`；一页 5 条（`schema.rs:89` 默认，用户 `default.yaml:40` 实为 `page_size: 5`） |
| 对外暴露 | c_api 永远只渲染第 0 页 | `c_api.rs:727` |
| 翻译器发射 | 流式（`peek`/`next`） | `translation.rs:27-32` |
| 多翻译器归并 | 每次取当前最优，不做全量排序 | `translation.rs:215-253` |
| 滤镜 | 包装流、逐条转换，不就地全量改 | `menu.rs:77-90` |
| 整句 | **先算完** DP，再装成一条候选 | `translator.rs:353-376` |
| 用户词 | **先查完**全部用户词候选 | `translator.rs:380-385` |
| 词表 | 收集器**先全量建好**分组，再懒发射 | `translation.rs:141-156`（`collector.into_iter()`） |
| 形码 | 直接整包 `Vec`，没有懒 | `table_translator.rs:343,379` |

**结论（重要）**：懒化省的是**内存 + 滤镜开销 + 排序**，不是**首候选出现时间**。`Translator::query` 在返回流之前，已经把整句 DP、用户词典、`lookup_from_graph` 收集器全部算完（`translator.rs:390-403`）。所以「流式」目前只到**发射层**，没到**查词层**。

另注：`translation.rs` 里的 `drain` / `drain_opt` 是 `#[cfg(test)]` 测试助手（`translation.rs:61-75`，`PROGRESS.md:1449-1451`），**不进生产链路**，别当成 API 用。

### 3.3 还缺什么：从按键到候选窗可见

| 段 | 现在做什么 | 还在等全量？ | 证据 |
|---|---|---|---|

**三条判断**

- 真正的卡点只有两个：① 引擎整段算完才返回；③④ 回包之后才发下一帧。其余都是配套。
- 通道（⑤）和渲染循环（⑥）已具备多帧能力，改造重心在引擎侧和快照发送时机，不在协议。
- ⑦ 意味着「先给一帧只有 preedit 的窗口」当前**看不见**（inline 模式下 `external_preedit` 为假）。要做零等待，要么改可见性判据，要么新增「候选窗骨架帧」。

**结论（四条）**

1. **一键一帧，没有中间帧**：Renderer 帧数 ÷ 按键事件数 = **2.00**（按下、抬起各画一帧）
   ⇒ 每按下一个键只出 **1.0 帧**，与 M5「流式后 ≥2」相差一整个量级。`publish` 仍在 `reply` 之后、一键一次。
2. **M1 只在短词上合格**：16.7 ms 判据下，短组合 0/512 超标；长组合 172/800 超标
   （按下 P95 27.2 ms、P99 30.5 ms、max 39.3 ms）⇒ 体感就是「打短词跟手，长句越打越顿」。
3. **M2 就是主因**：Engine 按下耗时 ≈ Tip 等待（14.4→13.1、1.9→1.8），中间只差 **1.0–1.3 ms**
   （RPC＋序列化＋队列）⇒ 该动的是引擎 `process_key`，不是协议。
4. **组合越长越贵**（长组合按轮内位置，Engine 按下 P50）：第 1 字 5.2 ms → 第 6 字 15.0 ms →
   第 14 字 20.8 ms，第 19 字后回落到 5–8 ms（疑似段内搜索被截断/换段）。这正是 `Translator::query` 全算的形状。

M6（首候选出现时 preedit 多长，要抓图）、watch 容量 1 会不会真丢帧、「首屏优先」能省多少。
