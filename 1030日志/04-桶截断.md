# 桶截断：把最坏键从 43.75 ms 压到 10.90 ms（2026-10-30 03:20–03:50）

> 改动文件：`librime-next/src/dict/dictionary.rs`（唯一一个文件，约 25 行）
> 接口：**零改动**，不影响甲路正在改的 `menu.rs` / `translation.rs` / `runtime.rs`
> 实测条件：自然码双拼 `double_pinyin.ziranma`，输入 `tianqibucuo`（11 键），
> release，语法模型（`.gram`）开着，**逐键新建 Session 喂进去**（冷路径，最坏情况）

---

## 一、问题

`ScriptTranslator::query` 走的是
`sentence_candidates` → `best_sentence` → `Poet::make_sentence`，
`make_sentence` 的第一步是 `build_word_graph`：对每个 `[start, end)` 音节区间
查一遍词典，把**命中的全部词条**塞进桶里。

实测（`tianqibucuo`，每键一条）：

```
poet edges=39 entries=5312 eval=33266      ← 第 11 键
poet edges=39 entries=1928 eval=9023       ← 中间某键
```

* 每桶 130~190 条（同一个拼音串能匹配到的词全在里面）
* 全图 1928~5312 条
* `Poet::run_beam` 对每个 `start_pos` 取 top-7，再 × 每个 `end_pos` × 桶里**每一条**
  → `evaluate` 九千到三万三千次/键

而 `Dictionary::translate`（另一条路，DFS）只有 292 个节点、0.16 ms ——
**根本不是瓶颈**。之前猜的 `TableTranslator::make_sentence` 的 O(n²) 查库也**不是**：
拼音压根不走 `TableTranslator`。

### 为什么不封顶是浪费

束搜索每步最终只留 top-7。桶里第 33 条以后**永远不会被选中**
（它的权重比前 32 条低，而前 32 条里最多也只有 7 条能进 beam）。
所以那 5000 条里绝大部分是纯浪费。

## 三、代码

### 3.1 常量与开关（`dictionary.rs` 模块级）

```rust
const K_BUCKET_CAP: usize = 32;

/// 桶上限。`WEASEL_BUCKET_CAP=N` 可临时覆盖（调参/排查用）；进程内只读一次环境。
///
/// * `N > 0`：每桶最多留 N 条。
/// * `0` / `off` / `none`：**关掉截断**（回到补丁前的行为，用来做 A/B 对照）。
/// * 没设 / 解析失败：用 [`K_BUCKET_CAP`]。
fn bucket_cap() -> Option<usize> {
    static CAP: std::sync::OnceLock<Option<usize>> = std::sync::OnceLock::new();
    *CAP.get_or_init(|| match std::env::var("WEASEL_BUCKET_CAP").ok().as_deref() {
        Some("0") | Some("off") | Some("none") => None,
        Some(v) => v.parse::<usize>().ok().filter(|n| *n > 0).or(Some(K_BUCKET_CAP)),
        None => Some(K_BUCKET_CAP),
    })
}
```

`OnceLock` 保证 hot path 上只有一次原子读，不做系统调用、不加锁。

### 3.2 `lookup_from_graph` 里两处

**① 早退（在取文本之前）** —— 关键：桶满且这条权重进不了前 N 就**直接跳过**，
连 `entry_text()` 都不调。`entry_text` 要解字符串再分配一份 `String`，是采集阶段的大头。
权重在取文本前就能算出来，所以判断是安全的。

```rust
let cap_opt = bucket_cap();
// ...
let Some(entry) = accessor.entry() else { break; };
if let Some(cap) = cap_opt {
    if collector.get(&end_pos).is_some_and(|b| b.len() >= cap) {
        let w = entry.weight as f64 - K_WEIGHT_OFFSET + credibility;
        let worst = collector[&end_pos].iter().map(|e| e.weight)
            .fold(f64::INFINITY, f64::min);
        if w <= worst { accessor.next(); continue; }
    }
}
let text = self.table.entry_text(&entry);   // ← 走到这里才解字符串
```

**② 入桶后裁剪** —— 只在超限时才排序：

```rust
bucket.push(VocabularyEntry { /* ... */ });
if let Some(cap) = cap_opt {
    if bucket.len() > cap {
        bucket.sort_by(|a, b| a.cmp_weight_desc(b));
        bucket.truncate(cap);
    }
}
```

> 排序只在 `len > cap` 时触发，且桶最多长到 `cap + 1`，
> 所以排序代价是 `O(33·log33)` 而不是 `O(190·log190)`，
> 相比省下的三万次 `evaluate` 可以忽略。

## 四、怎么回滚 / 怎么复查

不用改代码，直接给引擎进程设环境变量：

```powershell
# 回到补丁前的行为（A/B 对照）

# 或者临时调成别的数
$env:WEASEL_BUCKET_CAP = "64"
```

引擎进程重启后生效（`OnceLock` 每进程读一次）。

## 六、还能再往下挖的点（留给后续）

1. **桶内的 `evaluate` 还在全跑**。真正彻底的做法是让 `Poet::run_beam` 在
   `end_pos` 这一层就只取桶里 top-K（比如 top-8），而不是遍历整桶。
   这一步动的是 `poet.rs`，**属甲路**，且会改变打分语义，需要重测输出一致性。
2. **`build_word_graph` 本身**：`tianqibucuo` 只有 39 条边，但每条边都要查一次词典。
   逐键输入时同一批 key 会被反复查（第 11 键查的 11 个 key，前 10 键全查过），
   按 `key` 记忆化还能再省一块。
3. **`Poet` 的 `evaluate` 是否真需要每键重算**：输入只加一个字符时，
   前面 10 个 `start_pos` 的子图是没变的，理论上可以增量。改动面较大。

按收益排序：1 > 2 > 3。本次只做了不需要动语义的那部分（桶截断）。
