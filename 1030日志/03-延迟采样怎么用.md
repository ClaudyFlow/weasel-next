# 按键延迟采样：怎么用（乙-1 插桩）

## 一句话

放一个空文件 `%APPDATA%\Rime-Next\key-latency.on`，正常打一段字，删掉文件，
把三个 CSV 发我。

## 开关

```powershell
# 开
New-Item -ItemType File -Force "$env:APPDATA\Rime-Next\key-latency.on"
# 关（采样只在开关存在时进行，删了就彻底不写盘）
Remove-Item "$env:APPDATA\Rime-Next\key-latency.on"
```

环境变量 `WEASEL_KEY_LATENCY=1` 也能开（自动化测试用）。
开关每 2 秒才查一次，不会每键 stat；不开时只有一次原子读，零开销。

## 产出（都在 `%LOCALAPPDATA%\Rime-Next\Logs\`）

| 文件 | 谁写的 | 量的是什么 |
|---|---|---|
| `key-latency.csv` | Tip（跑在**应用 UI 线程**上） | RPC 等待 + 整段 TSF 回调 |
| `engine-key-latency.csv` | Engine | `Session::process_key` 的耗时 |
| `renderer-key-latency.csv` | Renderer | 一帧从"拿到快照"到"画完" |

格式：

```csv
# key-latency.csv
at_ms,wait_us,budget_ms,outcome,eaten
12345,8420,80,ok,1
12361,26310,80,ok,1        ← outcome=total 的那行是整段 TSF 回调，wait_us 是总时长
# outcome: ok | timeout | disconnect | total

# engine-key-latency.csv / renderer-key-latency.csv
at_ms,us,eaten,composing
12345,7100,1,1
```

## 怎么看

* `outcome=ok` 行的 `wait_us` = **应用 UI 线程被这一键堵住多久**（用户感觉到的卡顿）
* 对应的 `outcome=total` 行 = 整段 TSF 回调（比 `ok` 多出来的部分就是 Tip 自己的开销）
* `engine-key-latency.csv` 里同一时刻的 `us` = 引擎算多久
* 两者相减 ≈ RPC + 序列化 + 队列
* `renderer-...csv` = 候选窗落后多久（不阻塞打字，只影响观感）

关注点：
* 有没有 > 16 ms 的键（掉帧）
* 有没有 `outcome=timeout`（键被英文直通、相当于吞键）
* 长句后半段是不是明显变慢（引擎 `make_sentence` 的 O(n²) 特征）

## 已部署的组件

改动的三个二进制都要换进 `C:\Program Files\Rime-Next\Weasel-Next-0.18.5\`
（**需要管理员**）：

```
script\deploy-host-perf.ps1     ← 管理员 PowerShell 跑这个
```

它会自动停掉 Server/Engine/Renderer → 覆盖 `Weasel-Next.dll`、
`Weasel-Next-Engine.exe`、`Weasel-Next-Renderer.exe`、`weasel_theme_official.dll`
→ 重新拉起服务。日志在 `C:\Code\_logs\deploy-host-perf.log`。

32 位 TIP（`Weasel-Next-32.dll`）要单独编（`script\build-tip32.ps1`），本次没更新，
32 位应用里的输入法仍是旧版（不影响 64 位应用）。
